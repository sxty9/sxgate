# Deployment — one sxgate per environment

This document is the design record for how sxgate is installed and operated **the same way on
every host**, and where it deliberately stops at another environment's boundary.

## Leitbild (binding)

1. Every environment has an sxgate.
2. Each sxgate manages everything of its own environment.
3. Each sxgate manages nothing of an environment it does not belong to.

Sentence 3 is a boundary in its own right, not a corollary of sentence 2. An sxgate knows no
foreign zone, holds no foreign credentials, writes no foreign routes and starts no foreign
services. Reaching past its own environment is a fault even when it works.

There is **no** "production" special case. On every host the same program does the same thing:
it fronts the services running **on that host** under **that host's zone** — routes, mail egress,
mail inbound, preview. Same program, same commands, same paths. The only difference between two
hosts is their runtime configuration: which zone, which tunnel, which credentials. Those values
live in the runtime config and never in this repository, and they never justify a branch in the
code.

## The five responsibilities

| # | Responsibility        | What sxgate owns on this host                                        |
|---|-----------------------|---------------------------------------------------------------------|
| 1 | Tunnel + routes       | `cloudflared` config + the managed zone's ingress table             |
| 2 | SSH over the tunnel   | a service with an `ssh://` scheme — no special command              |
| 3 | Mail egress           | a DKIM-signing loopback relay handing off to a smarthost            |
| 4 | Mail inbound          | a Cloudflare Email Worker → the maild webhook through the tunnel    |
| 5 | Preview sandboxes     | a wildcard ingress → a dispatcher + one instance per live preview   |

All five are installed on every configured host — there is no partial install and no "here only
mail, there everything" switch. A host is provisioned or it is not.

## One command per host

```bash
sudo ./sxgate provision --zone <domain> \
     [--tunnel <name>] [--mail-domain <d>] [--mail-relay <host:port>] [--mail-relay-user <u>]
```

`provision` is the single access point for bringing a host up. It runs, in order and halting on
the first failure, the same subsystem bring-ups the operator would otherwise run one by one:
`setup` (cloudflared + tunnel + config scaffold) → `zone` → `mail setup` → `preview setup`. Every
step is idempotent, so `provision` also serves as "repair to the intended state" on an existing
host. It adds no second tool beside the CLI: it is a subcommand of the one `sxgate` CLI and reuses
the existing per-subsystem commands verbatim.

The single interactive moment is the Cloudflare login inside `setup` (a browser URL is printed);
on a host that already carries a cloudflared origin cert it is skipped.

## Runtime configuration — what a fresh host is told

Everything host-specific is runtime configuration, held under `/etc/sxgate` (and the mail
subtree). None of it is in the repository.

| Value              | Where it lives                          | How a new host gets it            |
|--------------------|-----------------------------------------|-----------------------------------|
| managed zone       | `/etc/sxgate/sxgate.conf` (`MANAGED_ZONE`) | `--zone` / `sxgate zone <domain>` |
| tunnel name        | `/etc/sxgate/sxgate.conf` (`TUNNEL_NAME`)  | `--tunnel` (default role name `sxgate`) |
| cloudflared config path | `/etc/sxgate/sxgate.conf` (`CONFIG_FILE`) | default; overridable             |
| mail domain / smarthost | `/etc/sxgate/mail/mail.conf`        | `--mail-domain` / `mail relay set` |

## Secrets are born where they are kept

DKIM keys, smarthost credentials and tunnel credentials are generated **on the host that keeps
them** and are never copied between hosts and never written into the repository. Each host has its
own:

| Secret                | Path (this host only)                     | Genesis                          |
|-----------------------|-------------------------------------------|----------------------------------|
| tunnel credentials    | `~/.cloudflared/<tunnel-id>.json`         | `cloudflared tunnel create` (in `setup`) |
| Cloudflare origin cert| `~/.cloudflared/cert.pem`                 | `cloudflared tunnel login` (in `setup`) |
| DKIM keypair          | `/etc/sxgate/mail/dkim/private.pem`       | generated by `mail setup`        |
| mail edge secret      | `/etc/holistic/mail-edge-secret`          | generated by `mail setup`        |
| mail inbound secret   | `/etc/holistic/mail-inbound-secret`       | generated by `mail setup`        |
| smarthost password    | `/etc/sxgate/mail/smarthost-pass`         | entered at `mail relay set`      |

A new host generates its own on first `provision`; nothing is transported from another host.
`.gitignore` keeps the tunnel credentials and cert out of the repository.

## Why preview instances remain multiple

Merging historically-separate units under one access point is the rule; a preview instance is the
justified exception. Each live preview is a distinct branch of a service, built and run in
isolation on its own loopback port with its own systemd instance (`sxgate-preview@<slug>`). They
are factually — not historically — multiple: one per running preview, created and destroyed on
demand. The one always-on part (the dispatcher that multiplexes previews by Host) is a single
unit; the per-preview backends are instances of one template. There is one template and one
dispatcher, not N hand-written units.

## Boundary — measured, not asserted

Sentence 3 was checked against the code and configuration of this repository:

- **No environment detection.** No code path branches on hostname, IP, or the presence of a file
  to decide "production vs. home". The only `hostname` references are DNS routing (ingress
  hostnames) and feature detection (`command -v …`); `os.Hostname()` in the egress relay is this
  host's own name used for its SMTP greeting, not a decision input.
- **No reach past the environment.** sxgate edits only local files (`/etc/cloudflared`,
  `/etc/sxgate`), talks only to the local systemd and the local cloudflared, and holds only this
  host's zone and credentials. It never SSHes to another host, never holds another host's zone,
  credentials or routes, and cannot change another environment. The `ssh` references in the docs
  describe how a *client* reaches **this** host through the tunnel — inbound, not outbound.
- **What crosses a host boundary is the delivery chain's job, not sxgate's.** sxgate transports
  nothing from one host to another.

If two sxgate hosts run side by side, a search over the configuration and state of one finds
nothing of the other, and either host failing leaves the other untouched — they share no state and
no dependency.

## Operator: one-time step on an existing host

A host already running an older sxgate needs one thing to converge on this model: re-run
`sudo ./sxgate provision --zone <its-own-zone>` (with its mail relay flags if it sends mail). It is
idempotent — existing cloudflared, tunnel, config, DKIM key and units are detected and preserved;
only what is missing is added. Nothing already in operation (routes, SSH access, mail egress) is
torn down or restarted beyond the reloads the individual subsystem commands already perform.

## Open: integration with the shared delivery receiver

The shared production receiver (`deploy/devlab-deploy-recv`) installs one prebuilt daemon per repo
(`/opt/<repo>/bin/<repo>d`) under a single confined unit that runs as an unprivileged
`User=<repo>` account, generated from one fixed template; it never builds on the target. sxgate's
work — writing `/etc/cloudflared`, reloading the cloudflared unit, generating DKIM keys under
`/etc`, creating preview systemd instances — is root-level system administration that a confined
`User=sxgate` unit structurally cannot perform, and the receiver's unit template cannot be
customized from this repo.

Closing that gap without touching the receiver (which stays free of any per-repo branch) requires
either a receiver/build-side change or a privilege grant to the sxgate account — both decisions
that belong to a supervised, approvable step, not to this repository alone. Until then, sxgate is
installed on each host by cloning it and running `sxgate provision` (above), which realizes the
leitbild — one sxgate per environment, same program, same commands, config-only difference — on
every host uniformly.
